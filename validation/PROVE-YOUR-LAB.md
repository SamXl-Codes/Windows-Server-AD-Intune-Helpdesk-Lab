# Evidence pack for the completed infrastructure lab

**Purpose:** Make the specific Windows Server 2022 / AD DS / Group Policy / Entra ID / Intune / osTicket skills stated in the CV independently inspectable. The owner has confirmed completing these activities. The public repository currently contains reproducible scripts and documentation, but **the original deployment screenshots and exports have not yet been supplied**. Do not imply otherwise.

## Where the real evidence comes from

Use your own Windows Server VM, joined Windows test device, Microsoft Entra/Intune test tenant and osTicket test instance. If the original lab no longer exists, recreate the relevant tasks in a *new, dated demonstration* and disclose that it is a reproduction. Never portray a reconstructed demonstration as a historical capture.

Save originals **locally** in `evidence-local/originals/` (gitignored). Make redacted copies in `evidence-local/captures/` (also gitignored). Only publish redacted copies you have inspected under `assets/evidence/`. A screenshot generated by ChatGPT, from Microsoft Learn, or from the existing synthetic Python report is **not** proof of an actual deployment.

## Read-only commands you can run locally

Run **only** on machines and domains you control or are authorised to administer.

### Domain controller / AD DS

Open PowerShell with the required AD module:

```powershell
Get-ComputerInfo | Select-Object WindowsProductName, OsName, OsVersion, OsBuildNumber
Get-WindowsFeature -Name AD-Domain-Services | Select-Object Name, InstallState
Import-Module ActiveDirectory
Get-ADDomain | Select-Object DNSRoot, DomainMode
Get-ADOrganizationalUnit -Filter * | Select-Object Name
Get-ADGroup -Filter "Name -like 'SG-Lab-*'" | Select-Object Name, GroupScope
```

Use test users and groups. For your own example domain, replace `SG-Lab-*` with the test group naming pattern you actually used. The existing `scripts/Get-LabADInventory.ps1` intentionally refuses domains other than `corp.lab.example`; do not bypass its safety gate to export an employer's production directory.

### GPO and joined client

On an authorised machine with the GroupPolicy module:

```powershell
Import-Module GroupPolicy
Get-GPO -All | Select-Object DisplayName, GpoStatus
# Contains security filtering, links, settings and other possibly sensitive details: local only.
Get-GPOReport -All -ReportType Html -Path "$env:TEMP\gpo-private.html"
```

On a client receiving Group Policy:

```powershell
gpresult /r
gpresult /h "$env:TEMP\rsop-private.html"
```

Review these private reports before sharing. Demonstrate at least one specific policy applying, rather than merely a GPO existing.

### Windows test device / Entra

```powershell
dsregcmd /status
# Or use the repository's local-only, redacting diagnostic helper:
.\scripts\Get-EndpointEnrollmentEvidence.ps1 -OutputDirectory .\evidence-local
```

The full `dsregcmd` output may contain identifiers, URLs and certificate information. **Do not upload it unredacted.** It is useful for device registration/join diagnosis, but it does **not** by itself prove Intune compliance, successful app deployment or MFA enforcement.

### Microsoft Intune / Entra admin portals

Capture the **real** test device from **Devices > All devices**. Then separately capture its **compliance** result, an **app installation** status, **Windows update ring** assignment/result and evidence of your MFA configuration/test. Remove tenant IDs, primary-user names, emails, serial numbers, device IDs and sensitive URLs before publishing. A setting marked `Assigned` is not proof it was applied successfully. <https://learn.microsoft.com/en-us/intune/intune-service/protect/compliance-policy-monitor>

### osTicket

From **Admin Panel > Manage > SLA Plans**, capture the configured test SLA plan. From **Agent Panel > Tickets**, capture a test ticket's categorisation, owner/queue, status, timestamps, and documented resolution. Create **fictional test tickets**, never upload real customers' records. <https://docs.osticket.com/en/latest/Admin/Manage/SLA%20Plans.html>

## Privacy and provenance

1. Take **real screenshots** in the relevant system, preferably including a neutral product title and relevant state. Use Windows Snipping Tool (`Win + Shift + S`).
2. Keep the unedited original locally, outside Git. Record the capture date and environment. Do not publish original unredacted exports.
3. Redact or **crop** users, emails, tenant IDs, GUIDs, IP addresses, machine names, ticket content, recovery keys, passwords, authentication tokens and other sensitive identifiers.
4. Make sure the redaction cannot be reversed (flatten exported PNG/JPEG). Review every visible field.
5. Store a descriptive, redacted PNG under `assets/evidence/` with a meaningful name (for example `e05-gpo-applied-redacted.png`). The existing demo screenshots belong in `assets/screenshots/` and must remain clearly identified as synthetic.
6. For each screenshot, add to the evidence index its filename, capture date, source environment, what it proves and what it **does not** prove. A screenshot only evidences the visible state, not every technical claim.
7. Run `scripts/New-LabEvidenceManifest.ps1` on the local redacted captures to obtain file hashes and an inventory **before** uploading the final redacted images. Hashes support integrity tracking; **they do not authenticate the deployment**.
8. Update the README's evidence-status table only after reviewing the actual images or reports. Use `Not independently verified` for any remaining gaps.

**Publishing warning:** The evidence script does **not** upload, inspect, redact or approve files. It is your responsibility to assess whether each screenshot can be publicly shared. Never commit original unredacted domain/tenant exports.
